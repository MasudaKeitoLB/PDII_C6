# 設計：タスク1「サーバーにつなぐ（保存・送信・オフライン）」

作成：2026-11-13　状態：案（チームの確認待ち）
対応する要件：M-01・M-02・M-06・M-14・N-12・N-13・N-19・12章　／　タスクの一覧：[MVPの残りタスク](MVPの残りタスク.md)

## 1. 方針

| 項目 | 決めたこと | 理由 |
| --- | --- | --- |
| つなぎ方 | fetch で Supabase の RPC（`/rest/v1/rpc/…`）を直接呼ぶ。ライブラリは足さない | 使うのは RPC だけ。オフラインは自前で扱う。supabase-js は gzip で約 52〜56kB 増える。PR #4 と同じ形 |
| ブラウザに置くキー | publishable key（`sb_publishable_…`）だけ | 公開してよいキー。secret key はブラウザでは使えない |
| 表の守り方 | 表は schema `hoho` に置き、Data API に出さない。RLS を有効にし、anon には表の権限を付けない。開けるのは `security definer`・`set search_path = ''` の RPC だけ | ブラウザから表を直接読めないようにする。definer の関数は誰の行でも返せるので、関数の中で必ず本人を確かめる |
| 利用者の本人確認 | 自前の合言葉（トークン）。登録のときに端末で作り、サーバーにはハッシュだけを置く。ほかの RPC には毎回トークンを渡す | メールの無い高齢者でも使える。オフラインでも登録できる。匿名サインインは端末を変えると戻れず、IPごと1時間30回の上限があり、教室での一斉登録でぶつかるおそれがある |
| 画面とデータ | `store.ts` の同期の形は残す。変わった所を「送信待ち」に積み、裏で送る | 画面・38件の動作テスト・33件の単体テストを変えずに済む |
| 接続の値が無いとき | 今までどおりブラウザの中だけで動く（送信待ちも作らない） | デモ・テストを守る |

## 2. 全体の流れ

1. 画面は、今までどおり `store.ts` の関数を呼ぶ。
2. 接続の値があるときだけ、`store` は変更を送信待ちに積む。キーごとの最新の値で上書きする（例：その日の合計歩数）。
3. `lib/sync.ts` が、合図のときに1回の RPC（`push_changes`）にまとめて送る。
4. 送れたら、サーバーが受け取った時刻が返る。それを `lastSyncAt` に入れ、送った項目を送信待ちから消す。
5. 登録は端末の中で先に済ませ、送信待ちの先頭としてサーバーに届く（オフラインでも登録できる）。
6. この端末に控えの無い人がログインしたときだけ、サーバーに照合し（`login_user`）、記録を取り込む（`pull_user`）。

## 4. 表と RPC

### 表（schema `hoho`）

| 表 | 主な列 |
| --- | --- |
| app_users（利用者情報） | id（uuid）、名前、名前のそろえ（NFKC＋空白なし）、誕生日、ローマ字1文字、ニックネーム、性別、身長、体重、1日の目標歩数、文字の大きさ、ふりがな、介護レベル、施設ID、担当ケアマネージャーID、登録日時、プロフィールの変更日時、最後に受け取った時刻 |
| daily_records（日ごとの記録） | 利用者、日付、端末ID、歩数（0〜100000）、端末で記録した時刻、受け取った時刻。（利用者, 日付, 端末）で1行 |
| game_records（ゲームの記録） | 利用者、レベル、経験値、ポイント、次の敵までの歩数、次の敵、累計の経験値、更新日時（画面用の `pending` は送らない） |
| share_consents（共有と同意） | 利用者、共有先（施設／ケアマネージャー）、同意しているか、同意した日時、やめた日時、変更日時 |
| user_tokens（補助） | トークンのハッシュ、利用者、端末、作った日時、最後に使った日時、失効した日時 |
| login_attempts（補助） | 名前と誕生日のハッシュ、失敗の回数、待たせる期限 |

- 距離とカロリーは列にしない。M-04・M-05 が決まっていないので、`health.ts` で毎回出す。決まったら列を足す。
- 管理者アカウントの表は、タスク2で作る。

### RPC（すべて definer。登録以外は、はじめにトークンから本人を引き、引数の利用者IDは信じない）

| RPC | 受け取るもの → 返すもの | 確かめること |
| --- | --- | --- |
| register_user | 利用者ID、端末ID、トークン、プロフィール、共有、ゲーム、登録日時 → 受け取った時刻 | 値の範囲（名前1〜40字、誕生日、文字は A〜Z か無し、身長・体重・目標は画面で選べる範囲）。同じIDとトークンの再送は成功、ちがえば `already_exists` |
| login_user | 名前、誕生日、文字、端末ID → ok（利用者ID・新しいトークン）／no／wait（待つ秒数） | 照合は今の端末と同じ規則。5回失敗で1分待ち、そのあと2倍、最大15分。いない人でも同じ動きにする |
| pull_user | トークン、端末ID → プロフィール、共有、ゲーム、日ごとの歩数（この端末の分・ほかの端末の分）、最後に受け取った時刻 | トークンが有効か |
| push_changes | トークン、端末ID、変更（最大200件） → 受け取った時刻 | 歩数は大きいほうを残す（再送で減らない）。日付は登録日の前日〜今日の翌日。ゲームは累計の経験値が増えるときだけ。プロフィールと共有は、変更日時が新しいときだけ |
| revoke_token | トークン → なし | — |

### 計画で決めたこと

- **同じ人が別の端末で歩いたら**：端末ごとの行を足し合わせる。2台を使っても減らない。端末は自分の分だけ送るので、再送しても増えない。画面には「この端末の値」と「サーバーの合計」の大きいほうを出す。
- **新しい端末でログインしたら**：`pull_user` で記録とゲームを取り込む（タスク1に入れる）。ゲームはサーバーでも端末でも累計の経験値が大きいほうを残すので、新しい端末が上書きして消すことはない。
- **いつ時点のデータか（N-19）**：`lastSyncAt` は、送れたときにサーバーが返す時刻にする。

## 5. テスト

- **単体**：接続の値の確認（http を断る、ヘッダーの付け方）、送信待ち（上書きで1件、登録が先頭、送っている間の上書きは消さない、再送で増えない、再送の間隔、200件で区切る、取り込みの合わせ方）、累計の経験値。
- **今の動作テスト38件**：接続の値なし（`dev:e2e`）で、変わらず通ること。
- **新しい動作テスト `e2e/sync.e2e.mjs`**：存在しないアドレス（`hoho-e2e.invalid`）をにせのサーバーで受ける。
  - 登録すると、登録が先に届く
  - 通信なしで歩き、戻すと合計が一致して届く
  - 2回送っても増えない
  - 別のブラウザでログインすると、歩数とレベルが出る
  - 控えが無く通信も無いときは「通信できません」と出る
  - 5回まちがえると待たされる
- **実サーバー**：開発用プロジェクトで `check-server.mjs`。スマホで歩く → 機内モード → 戻す → 表に行が入る。

## 6. 危ない所と対策

| 危ない所 | 対策 |
| --- | --- |
| iPhone で動きの許可が出なくなる | サーバーでのログインのときだけ、待つ前に許可を出す。登録は同期のまま |
| `crypto.randomUUID` が使えない（http の LAN で開いたとき） | `getRandomValues` で作る |
| 接続の値がテストやデモの成果物に入る | モードのファイルで値を空にする |
| definer 関数で本人確認が漏れる、public の実行権限が残る | 本人は共通の関数で必ず引く。権限は SQL の最後でまとめて外し、必要な分だけ開ける。`check-server.mjs` で他人のトークンと表の直接読みを試す |
| トークンを localStorage に置く | 外の script を入れない。ログアウトで失効できる |
| 登録の乱発（誰でも呼べる） | 値の範囲で絞る。必要なら件数の上限を足す |
| 端末の時刻がずれている | 日付の範囲を確かめる |
| 無料枠は1週間使わないと止まる | 止まっても送信待ちに残るだけ。発表の前に開いておく |
| PR #4 と重なる | `staffAuth.ts` は、タスク2で `server.ts` を使う形にそろえる |

## 7. チームに決めてもらうこと

1. Supabase の持ち主、開発用と本番用の2つを作るか、接続の値の渡し方（チャットに貼らない）
2. 本人確認の強さ：ローマ字1文字が無い人は名前と誕生日だけで入れる今の規則でよいか。待たせる回数と時間（案：5回で1分、最大15分）
3. 登録のトークンを端末で作ってよいか（オフラインで登録でき、再送しても同じ結果になるため）
4. トークンの期限（案：期限なし、ログアウトで失効。M-02「次から入力しなくても使える」に合わせる）
5. 施設IDと担当ケアマネージャーIDを、端末が決めてよいか（タスク3の「見せる範囲」にかかわる）
6. サーバーにつないだときの「はじめの状態にもどす」・サンプルの利用者・30日分の記録（案：端末だけ消す、サンプルは出さない、30日分は送らない）
7. 古い試作で登録した人を引き継ぐか（案：引き継がない）
8. ホームの「○○ 更新」を、サーバーに届いた時刻にしてよいか（通信できない間は時刻が進まない）
