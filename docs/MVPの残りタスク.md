# MVPの残りタスク（1〜3）

作成：2026-11-13　状態：案（チームで確認してから着手する）

MVPの残りは、サーバーにつなぐ作業が中心になる。次の3つを、この順番で進める。前のタスクが終わらないと、次のタスクは動かない。

| 順 | タスク | 対応する要件 | 前提 | 完了の目安 |
| --- | --- | --- | --- | --- |
| 1 | サーバーにつなぐ（保存・送信・オフライン） | M-06、N-12、N-19 | Supabase の接続の値 | 歩いた記録がサーバーに入る。通信できないときも記録が残り、戻ったら届く |
| 2 | 管理者のログインをサーバー側にする | M-15、N-13 | タスク1、PR #4 | 正しいIDとパスワードだけで入れる。ブラウザからパスワードも他人のデータも読めない |
| 3 | 共有・一覧・測定結果をサーバーのデータで動かす | M-14、M-16〜M-19、N-14、N-19 | タスク1・2 | 別の端末で歩いた結果が、同意した利用者だけ管理者画面に出る |

## 進め方

- 各タスクは、`CLAUDE.md` の流れで進める。調査 → 計画 → 実装 → テスト → 原因調べ（最大3回）→ レビュー → 報告。
- 1タスクにつき、ブランチとプルリクエストを1つ。ブランチは main から切る。
- PR #5（Android版）が main に入ってから始めると、`AppState.tsx` のぶつかりが少ない。

## 今のコードの状態（確かめたこと）

- データは `lib/store.ts`（ブラウザの localStorage）に入っている。画面は `useStore` で読む。
- 管理者のアカウントは `lib/admin.ts` の `ADMIN_ACCOUNTS` に、パスワード付きで入っている（デモ用）。ログインの確認は `checkAdminLogin`（ブラウザ側）。
- 管理者の一覧は `screens/admin/adminData.ts` が、ブラウザの中の `getStore().users` から作っている。
- PR #4（ri1213ts さん）は、Supabase の RPC `is_staff`（名前の判定）と `authenticate_staff`（名前と暗証番号の照合）を呼ぶ `lib/staffAuth.ts` と、暗証番号の画面を足している。今の管理者画面（`AdminLoginForm.tsx`）にはつながっていない。テーブルや RPC を作る SQL は、リポジトリに無い。
- `user-app/.gitignore` は `*.local` を無視するので `.env.local` は守られる。`.env` は無視されない。
- 起動時に `main.tsx` と `AppState.tsx` が `ensureSampleData`（サンプルの利用者づくり）を呼ぶ。デモと動作テストはこれに頼っている。

## タスク1：サーバーにつなぐ（保存・送信・オフライン）

**ねらい**：利用者の記録をサーバーに置く。通信できない場所でも歩数を記録し、戻ったら送る（M-06、N-19）。通信は暗号化する（N-12）。

**設計**：[設計-タスク1-サーバー接続](設計-タスク1-サーバー接続.md)（2026-11-13、案）

**前提**：チームが Supabase のプロジェクトと接続の値（URL と公開用のキー）を用意する。

**作ること**

1. 準備
   - 接続の値は、コードに書かず `user-app/.env.local` に置く。`.gitignore` に `.env*` を足し、値を空にした `.env.example` を置く。
   - Supabase の持ち主と、値の渡し方（チャットに貼らない方法）を決める。
2. データの置き場の設計。SQL は `supabase/migrations/` に置いて、リポジトリで管理する。
   - 表：利用者情報、日ごとの記録（利用者・日付・歩数・距離・カロリー。1人1日1行）、ゲームの記録（経験値・レベル・ポイント・主人公の状態）、共有と同意の記録（共有先・同意した日時・やめた日時）。管理者アカウントの表はタスク2で作る。
   - 位置情報の表は、移動距離の出し方（M-04）が決まるまで作らない。
   - 読み書きの方法：表を直接読ませず、RPC（関数）を通す案。PR #4 と同じ考え方。
3. 接続の部品 `lib/server.ts`（新規）：PR #4 の `callRpc` を共通にして、`staffAuth.ts` もこれを使う。接続の値が無いときは、今までどおりブラウザの中だけで動く（デモ・動作テスト・単体テストが変わらないように）。`ensureSampleData` は、このときだけ呼ぶ。
4. 送信と送信待ち：`store.ts` の保存は「端末の控え」として残し、まだ送っていない変更を順番に並べる。通信できたら古い順に送る。
   - 記録は「その日の合計」で送る（足し算ではなく上書き）ので、再送しても二重に増えない。
   - 対象：`recordSteps`（2秒ごとのまとめ）、`registerAppUser`、`setGoal`、`updateProfile`、`setShare`。
5. 登録とログイン：`registerAppUser` と `loginAppUser` をサーバーにもつなぐ。端末には利用者IDだけを持つ。通信できないときは、控えのある端末なら今までどおり入れる。
6. 暗号化の確認（N-12）：接続先が `https://` でないときは、起動時に止める。

**テスト**

- 単体：送信待ちの順番、再送しても二重に増えない、通信なし → 通信が戻る。
- 動作（Playwright）：`context.setOffline(true)` で歩く → つなぎなおす → 送られる。サーバーは `fetch` の置きかえで代用する。
- 実サーバー：Supabase の表に行が入ることを、画面で確かめる。
- 今ある 33 + 38 のテストが、接続の値なしで変わらず通ること。

**完了の目安**：歩いた記録がサーバーの表に入る。機内モードで歩いても、つなぎなおすと届く。値が無いときは今までどおり動く。

**チームで決めること**：Supabase の持ち主・無料枠の条件、RPC を通す方法でよいか、利用者の本人確認（名前・誕生日・ローマ字1文字で足りるか。16章「ログインの安全性」）。

## タスク2：管理者のログインをサーバー側にする

**ねらい**：管理者側のパスワードの確認を、ブラウザではなくサーバーで行う（M-15、N-13）。今は `hoho-2026` がブラウザに入っていて、安全ではない。

**前提**：タスク1（接続の部品とデータベース）。チームの PR #4。

**作ること**

1. 先に決める：管理者ログインの形。
   - 要件定義書（M-15・N-13、11/6）：名前の欄にID → パスワード。
   - PR #4：名前 → 暗証番号（数字4桁以上）。名前が管理者かどうかを `is_staff` で判定する。
   - どちらかに合わせて、要件定義書かコードを直す。案：要件定義書どおり ID + パスワード。PR #4 の考え方（照合はDBの中で、表をブラウザに返さない）は活かす。
2. ログインのあとの本人確認：PR #4 の RPC は true か false を返すだけなので、そのあとの「一覧を見る」で誰かを確かめられない。ログインが通ったら、期限つきの合言葉（トークン）か Supabase Auth のセッションを渡し、タスク3の取得で毎回サーバーが確かめる。案：Supabase Auth（管理者アカウントは運営者が作る）。行ごとの権限（RLS）で、同意した利用者だけを守れる。
3. 管理者アカウントの表：ID、氏名、所属（施設かケアマネージャーか）、施設ID、パスワード（ハッシュで保存）、見られる利用者（ケアマネージャーの担当）。運営者が発行する手順を README に書く。
4. 画面：`AdminLoginForm.tsx` の `checkAdminLogin` を、サーバーでの照合にする。確認中の表示と、通信できないときの案内を出す。間違ったときは、今までどおり「パスワードが違います」だけを出し、IDとパスワードのどちらが違うかは言わない（N-13）。ログアウト（`setAdminSession(null)`）で合言葉を捨てる。
5. `ADMIN_ACCOUNTS` のパスワード入り（デモ用）は、ブラウザの中だけのモードに残し、サーバーのモードでは使わない。
6. 総当たりの対策：何回か間違えたら、サーバー側で少し待たせる。
7. PR #4 の扱い：先に main に入れる（`docs/memo.txt` への1行の追加に、秘密の値が入っていないか、入れる前に確認する）か、このタスクで中身を取り込んで閉じるかを、チームと決める。

**テスト**

- 正しいとき、間違ったとき、存在しないID。施設スタッフとケアマネージャーの切り替え。期限切れ。
- 公開用のキーだけで表を直接読むと、空になる（パスワードも他人のデータも読めない）。

**完了の目安**：正しいIDとパスワードだけで管理者画面に入れる。開発者ツールからも、パスワードや他人のデータが見えない。

**チームで決めること**：ログインの形（要件定義書か PR #4 か）、ログイン後の本人確認の方法（Supabase Auth か自前の合言葉か）。

## タスク3：共有・一覧・測定結果をサーバーのデータで動かす

**ねらい**：利用者と管理者が、別の端末で同じデータを見られるようにする（M-14、M-16、M-17、M-18、M-19、N-14、N-19）。

**前提**：タスク1・2。

**作ること**

1. 共有（M-14）：`setShare`（同意・やめる）をサーバーに保存し、同意した日時とやめた日時を残す。やめたら、すぐ管理者から見えなくなる（N-14）。
2. 一覧（M-16）：見せる範囲をサーバーが決める。施設スタッフは同じ施設で同意した人、ケアマネージャーは担当で同意した人。返す項目は、名前・年齢・介護レベル・本日の歩数・目標・最後に届いた時刻だけ（位置は返さない、N-15）。並べ替えと名前の検索は、今の `sortSummaries` と `matchesName` を使う。`adminData.ts` がブラウザの中のデータを見ている部分を、サーバーから取る形に替える。
3. 測定結果（M-17・M-18）：日ごとの記録（1週間・1か月）をサーバーから取る。距離とカロリーは、今の `health.ts` の計算を使う（M-04・M-05 の方法が決まったら見なおす）。
4. いつ時点のデータか（N-19）：一覧と測定結果に、サーバーに最後に届いた時刻を出す。今の `lastSyncAt` と `notReceivedToday` を、サーバーの値にする。
5. 目標歩数（M-19）：管理者画面の `GoalDialog`（管理者が利用者の目標を変える）もサーバー経由にし、見られる利用者だけに許す。
6. 読み込み中と失敗の表示：「読み込み中」と「通信できません。もう一度」を出す。スマホ版・PC版の4画面（`AdminListScreen`・`AdminUserScreen`・`AdminPcListScreen`・`AdminPcUserScreen`）すべて。一覧は、一定の間隔（案：30〜60秒）か「更新」ボタンで取りなおす。
7. プライバシーの確認（N-14・N-15・N-16）：同意していない利用者、ほかの施設、担当でないケアマネージャーのデータが出ないこと。

**テスト**

- 2つのブラウザ（利用者と管理者）での通しの確認。
- 同意をやめると一覧から消える。担当でない人が見えない。通信できないときの表示。
- 単体：サーバーの値を表示用に直す部分。

**完了の目安**：端末Aで利用者が歩く → 同意していれば、端末Bの管理者画面の一覧と測定結果に出る。同意をやめると見えなくなる。
